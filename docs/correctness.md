# 正确性规则：怎么确认 lift 和分析的结果是对的

适用于所有改动语义的工作：lifter（IGNIL）、LLVM 降级、符号执行、切片器、加载器。
本项目没有形式化证明；正确性靠下面这套**差分验证**规则来保证。每个 agent 开工前都要读一遍。

## 1. 基本原则

1. **绝不输出错误语义。** 拿不准就输出 UNDEF，并调用 `Block::noteUnlifted(addr)`；手册规定"未定义"的结果也给
   UNDEF，不猜。一个看起来确定但错误的值，比诚实的 UNDEF 更糟。LLVM 层同理：不确定的效果要保守表示，
   不能让优化器据此推出结论（例如不能用 `unreachable` 表示"不知道去哪"）。
2. **正确性由独立的参考实现判定，不由代码作者判定。** 参考实现：Unicorn（用 `~/ucdev/bin/python3`，即修复了
   BZHI/BLSI 的 dev 版）。有疑问时用第二个参考（见第 4 节）。
3. **每个修复或新增都要有回归测试**，并确认它在旧代码上失败、在新代码上通过。没有经历过"失败"的测试，
   不能证明它测到了东西。

## 2. 验证分层（每层各管什么、不管什么）

| 层次 | 工具 | 能发现 | **覆盖不到** |
|---|---|---|---|
| 单指令 | `difftest_x64.py` / `difftest_sse.py` / `difftest_a64.py` | 单条指令的寄存器、标志位、内存语义 | 指令组合；真实代码里的少见形式 |
| 真实基本块（IGNIL） | `realblock_diff.py` | 指令组合、真实代码形式；`REALBLOCK_OPT=1` 检查优化器 | 块与块之间的控制流；call/jmp 在测试前被去掉 |
| 真实基本块（LLVM 原生执行） | `realblock_llvm.py` | IGNIL→LLVM 的翻译错误 | 同上；函数级控制流和调用边界（见 `docs/llvm-control-flow.md`） |
| IR 合法性 | `corpus_check.py`（`opt -passes=verify`） | 生成的 IR 不合法 | **语义**：IR 合法不代表结果正确 |
| 分析结果 | `truth_rel.py`、`table_truth.py`、`guard_truth.py`、`fstarts.py` 等 | 跳转表、函数入口等与真值不符 | 真值本身来自启发式（如 objdump、符号表）时的误差 |
| 鲁棒性 | `fuzz_loader.py` | 损坏输入导致的崩溃、卡死、意外异常 | 语义正确性 |

改动涉及哪一层，就必须跑那一层；改动影响到上游层（例如改了寄存器模型），下游各层都要跑。
当某类问题没有任何一层覆盖时，先补测试框架，再改代码（例如函数级 LLVM 执行对拍）。

## 3. 测试框架本身的规则

1. **新建或修改测试框架，要先证明它能抓出错误。** 做法任选其一：
   - 用旧代码（或刻意改坏的版本）运行，必须报出差异；
   - 提供一个会故意出错的对照变体（例如 `opt_equiv.py` 的 `CONTROL=1`）。
   例：SSE 对拍扩展到 128 位后，对旧代码运行报出 26 个差异、116 个未 lift，新代码 0 差异。
2. **测试输入必须覆盖边界值**，不能只用均匀随机数：0、1、−1、全 1、各宽度的符号位（0x80、0x8000、
   0x80000000、2^63）、最大最小值；浮点的 ±0、±inf、NaN、非规格化数、溢出边界；移位/位操作的计数取 0、1、
   位宽−1、位宽、超过位宽；比较类指令要让一部分输入的操作数相等。
3. **允许跳过或排除的情况只有这几种**，并且每一条都要在脚本里写明原因，在 `AGENTS.md` 里登记：
   - 手册规定为"未定义"的结果（例如移位超过 1 位后的 OF、bsf/bsr 源为 0 时的目的寄存器）；
   - 经第二个参考确认的参考实现 bug（例如 Unicorn 2.1.4 的 BZHI/BLSI；框架要能探测版本，修好后恢复比较）；
   - 参考实现的已知限制（例如 Unicorn 会截断 ≥2^47 的地址，这类试验跳过）；
   - 项目刻意的设计差异（见第 5 节）。
4. **不允许为了让测试通过而放宽对拍**：不能删掉失败的模板、不能扩大排除范围、不能把比较改成只比一部分，
   除非符合第 3 条并写明理由。跳过的数量要出现在统计输出里（例如 `skip: high address`），不能悄悄丢掉。
5. 结果统计要区分"比较了""跳过了（原因）""失败了"，汇报时给出全部数字。

## 4. 和参考实现不一致时怎么办

1. 先查手册（Intel SDM / ARM ARM），不预设任何一方正确。
2. 怀疑参考实现有错时，必须找**第二个独立参考**确认：
   - x86：在 Mac 上用 Rosetta 运行 x86-64 代码（`clang -arch x86_64`，`arch -x86_64` 运行），或真实 x86 CPU；
   - 也可以对比参考实现的更新版本（例如 Unicorn dev 分支）。
3. 只有手册和第二个参考都支持 dragon 时，才能判定是参考实现的错。此时：把正确值写进 C++ 回归测试（不依赖
   有 bug 的参考实现），在对拍脚本里按第 3 节第 3 条处理，并在 `AGENTS.md` 里记录。
4. 如果 dragon 和参考实现可能犯同一个错（共同误解），对拍发现不了；对有疑问的指令，主动用第二个参考抽查。

## 5. 已知的刻意差异（不算 bug，比较时排除）

- x86 移位超过 1 位后的 OF：手册规定未定义，dragon 按 1 位移位的规则给出确定值（VMProtect 会把标志位折叠进
  状态，见 `emitGatedShiftFlags`）；Unicorn 置 0。
- IGNIL 的 CALL 不压返回地址，RET 没有操作数（x86 和 ARM 都是）：AArch64 对拍里 `bl/blr/ret` 有 3 个预期差异。
  注意这只是 IGNIL 层的抽象；LLVM 层的调用边界问题另见 `docs/llvm-control-flow.md`。
- XMM 只建模到 bit 127（YMM/ZMM 的高位不建模）。

新增刻意差异前要先和仓库所有者确认，并登记在这里和 `AGENTS.md`。

## 6. 汇报要求

- 列出跑了哪些验证、每项的数字（比较数、跳过数及原因、失败数），以及未 lift 的前后对比。
- 失败要附上原始输出，不能只写"有几个失败"。
- 说明这次改动**没有被哪一层覆盖**（第 2 节的盲区），以及打算怎么补。
- 跳过了某个验证步骤，要明确说明原因。
