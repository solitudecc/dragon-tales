# 跨调用内存传递与确定循环的写入效果

2026-11-08，基线 `90da1f8`。在[调用者参数上下文](caller-context-memory.md)上，
把调用前已经证明的内存事实传给有界调用树，并分析由这些事实确定控制流的普通 CFG 循环。
调用证明仍为静态分析，继续通过 `prove_leaf_calls=True` 显式开启，默认关闭。
没有新增公共 C++/C/Python API、操作码或 Guest ABI。

## 内存上下文

调用者只传递与调用 SP 同一地址空间中已经证明的常量字节，以及存入内存的完整
SP 相对指针。地址换算为被调函数入口 SP 的偏移，限制在前后 1 MiB；数值 SP 锚点
也可以识别该范围内的确定绝对地址。它没有建立一般堆对象或全局别名模型。

缺失字节、多个可能值、不同符号基址和不完整指针继续未知。
32 位模式的高地址事实不会经截断被错误传到低地址。
机器 CALL 新压入的返回槽逐字节排除，不能把压栈前的旧内容当作入口值。
这些事实来自当前分析状态中的 STORE 或显式条件入口约束，没有读取运行时快照来补足证明。

嵌套调用按实际 SP 平移内存地址和内存中保存的指针，并再次排除子调用的新返回槽。
被调函数读取当前内存状态；循环中的每次 STORE 都影响后续 LOAD，因此重叠复制保持
真实的先读后写顺序。它不会把整个来源区域一次性保存后再复制。

两层调用缓存均包含完整内存约束。同样的寄存器、指针和目标函数，在来源内存从 7
改为 9 后不能复用旧结果。入口内存、构造工作和缓存占用受事实及操作预算限制。
只把本次确实写过、且正常返回时一致的常量作为写后结果导出。

原有任意输入证明可能已经成立，却只能给 LOAD 结果 Unknown。
私有精度提示允许这种调用用内存上下文再次证明；失败时保留已有的安全效果。
最后仍按实际数值 SP 检查所选写集，拒绝覆盖已解码代码的写入，包括重叠 x86 解码路径。

## 确定控制流与循环

先在给定约束下精确解释 CFG：只有 CJMP 的一位条件被完整计算为 0 或 1，
且两条目标与真实机器指令及 Graph 后继完全一致，才选择一条边。
循环迭代保持当前状态，不把不同计数的状态提前合并。达到真实普通 RET、证明 SP 恢复，
并通过返回槽、代码写入及预算检查后，才发布效果。

这能处理已知次数的普通填充和复制循环，包括零次、一次、多次及顺序重叠写入。
它不依赖循环的函数名、寄存器名称或固定序言；支持的操作仍限于现有 x86 E8/C3 调用证明域。
相同 SP 基址的指针可以证明相等或求模宽差值；无数值锚点时不会用偏移大小推断地址排序。

精确模式遇到未知条件或其他不支持的情况，会丢弃其局部状态、写集和结果，从同一入口约束
重新运行原有的全后继不动点分析。两次尝试共享每次调用树至多 4096 次操作的预算，
也共同计入外层全局预算。耗尽时不发布执行前缀或采样目标。
调用深度四层、每层 32 块及 8192 事实等限制保持不变。
证明描述正常返回时的效果，不承诺函数必定终止、无故障或满足真实操作系统的页权限。

同源异或也按快照身份证明：同一操作中相同寄存器字节，或已经定义且宽度一致的同一 Temp，
满足 `x ^ x = 0`。两个不同的未知 LOAD/UNDEF 不因抽象表示相同而被合并。
缺失 Temp、宽度不同或不同寄存器继续未知。该规则用于调用证明器，以及开启
`prove_leaf_calls` 的调用者分析，默认关闭的有限值集模式保持原结果。
这覆盖真实 helper 的 `0x1045d: xor r8d,r8d` 这种循环索引清零形式，不依赖该地址或函数名。

未知或过大的计数、一般符号循环归纳、REP 局部控制流、任意堆初始化、外部调用、
并发或自修改代码仍不在本组件范围内。调用者自身的普通有限值集循环仍采用保守汇合，
本组件没有为所有调用者循环增加精确执行，也没有实现自动去平坦化。

## 两项额外正确性修复

数值上下文中，callee 将 SP 写成恰好等于自身入口 SP 的常量后返回，旧摘要会把这个
callee 坐标的常量直接装回 caller。在 i386/x64 的实际反例中，调用者 SP 因而少了 4/8。
Unicorn 确认返回到 caller RET 前 SP 应为 `0xc800`；旧分析却给 `0xc7fc` / `0xc7f8`。
修复在证明正常返回恢复 SP 后，将实际 SP 字节规范化为入口身份；32 位写造成的其余
父寄存器字节效果仍按原规则处理。直接和嵌套调用均有永久回归。

另外，CALL 后立即继续循环曾跳过临时值预算核查，新增缓存事实与仍存活的 SSA Temp
未一起计入 `max_facts`。现在在 CALL 后按完整公式检查。
专门的资源回归只添加不改变机器状态的死 Temp，检查首次分析的预算状态，不依赖无效查询。

### 真实 Tigress 的有限收益和资源代价

采用原有八个条件内核执行前缀，不执行 wrapper/megaInit，不注入堆快照，保留真实
memset。每种最终配置的 192 个表单元查询中，`0x1004f` 为 24 Finite / 72 Unknown，
`0x1011b` 为 96 Unknown。已发布的有限集合都覆盖参考执行实际读到的值。
每种配置的 16 份报告中四份完成、12 份触及原有 1000000 操作预算；报告中的
`proven_calls=1 / rejected_calls=1` 是全 Graph 调用地址计数，不是每个 root 的证明。
直接前一版的对应结果是 192 Unknown、16 份完成、调用计数 0 / 2。

增加事实传播带来了条件值和调用证明收益，也显著增加了分析成本。预算失败的报告不发布
部分结果，不提高默认预算来掩盖退出。后续需要减少无关调用上下文的缓存差异，并控制
调用者循环中的状态增长。本文的 24 个可证明单元不是默认去混淆收益、完整 kernel 返回、
原程序初始化验证或自动去平坦化成功。
