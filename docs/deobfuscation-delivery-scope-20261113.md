# 通用分析框架与样本 pass 的交付边界

2026-11-13，仓库所有者确认按“通用框架 + 特殊样本 pass”推进。当前目标是
帮助理解混淆代码、恢复业务关系并支持 LLVM/pass 分析；独立二进制重建和通用
VM 去虚拟化不在本轮范围。此前方案与所有原始验收结果继续保留，不追认失败
为成功。

## 核心与扩展的分工

通用核心负责机器语义与 LLVM 提升、CFG/数据流、Guest 内存关系、已证明调用
效果、表达式与谓词化简、分发器/状态关系的通用证明、受控 CFG 改写、预算及
Unknown/Incomplete 报告、pass 接口和验证。算法按实际 IR 结构工作，不依赖
混淆器名称、样本地址或固定状态码。

样本 pass 负责特定保护的识别、编码规则、表结构、初始化约定和专门的状态
关系。它可向通用分析提供有出处且可验证的事实，或者在显式检查前提的独立
视图上分析。一般性基础缺陷继续修核心；依赖某种保护约定的处理留在扩展。
尚未证明的内存不变性、未知调用效果和分配成功不能直接变成优化前提。

样本 pass 的识别应优先使用结构、操作和数据关系。地址/符号可以作为用户
显式提供的定位信息，不能悄悄作为通用算法正确性的依据。失败路径、未知
调用、真实业务分支及未处理区域保留，并在报告中说明限制。

## 本轮收尾顺序

1. 提交已完成组件及独立正确性证据，补齐实现、验证范围和已知限制的文档。
2. 保留最后 combo O2 的实际失败。只做有限的目标级原因定位；发现明确的
   通用缺陷时修复并加入旧代码失败/新代码通过的回归；需要新保护模型时记录
   后续 pass 需求。一次默认 Guest-memory 重跑已实际未改变该 LOAD，不能把
   全模块预算/屏障计数当作该 LOAD 的具体失败原因。
3. 使用未参与本轮实现的新函数做小规模实用验收，冻结源码、编译选项、输入、
   参考实现和 pipeline，保留第一轮全部成功与失败。覆盖 MBA、代数谓词、
   普通控制流平坦化及组合，并包含非 Tigress 的手写结构。
4. 单独报告正确性、恢复精度、运行成本及人工可读性，依据新样本的实际收益
   决定下一批通用修补。特殊样本采用独立 pass 迭代。

不因“测试通过数量多”增加成功结论；也不把 contexts/copies 增长、已知地址
增加、条件入口闭环或原生正常输入匹配计作完整去平坦化。尚未实测的人工节时
不报告为已实现收益。

## 验收分层

| 层次 | 需要的证据 | 结果的边界 |
| --- | --- | --- |
| 正确性 | 相关完整测试、独立参考、边界输入与指定故障检出；比较完整约定状态 | 测试域内未观察到差异，不代表任意输入正确 |
| 精度 | 真实状态/分发关系、原始业务 CFG、完整 fallback 与残余路径的独立检查 | Unknown/Incomplete 和无法恢复的部分原样报告 |
| 实用收益 | 新函数的原始/处理后 IR 与 CFG、业务逻辑可追踪性、耗时/资源 | 与正确性分开；运行耗时不能替代人工分析耗时 |
| 可扩展性 | 一个最小样本 pass 的识别/事实来源/改写/验证流程与复用接口 | 定制规则不会自动升级成通用事实 |

新批次是独立实用报告，保留历史四档和所有原生/语料库门槛。顺序链目前为
cff O0/O2、combo O0 条件闭环通过，combo O2 未通过；完整循环去平坦化仍未
完成。组件可分别验证和交付，主线合并仍需完成适用于具体改动的验证并明确
记录限制，不得通过删除失败样本或放宽比较来通过。

单步诊断继续使用开始 512 MiB、运行 64 MiB、每命令 180 秒的既定资源限制；
新完整 campaign 的开始门槛仍为 1 GiB。空间不足先完成双端归档/文件集/hash
核对和依赖关闭，再退役精确的重复数据，不降低门槛。
