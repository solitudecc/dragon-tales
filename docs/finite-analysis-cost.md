# 有限值集分析的预算与 XOR 求集加速

基线 `a9f916d`。本阶段只改变有限值集求解的重复工作和整数 XOR 集合计算；公共 API、IGNIL、Guest ABI、调用效果证明器与 LLVM 优化步骤均未增加新语义。默认 `prove_leaf_calls=False` 也采用这些加速，不能沿用此前“默认操作计数完全不变”的说法。

## 固定跳转的报告阶段

不动点阶段仍解释每个可达块。报告直接常量 JMP 时，如果没有该块末尾的值查询，就直接报告目标常量；不再计算一个无人使用的块末状态。间接目标和普通值查询仍解释完整块，包含只查询常量的情况；内存查询仍按实际 LOAD 之前的前缀分组解释。未提升和局部控制流的块屏障、不可达状态与全局失败后全部 Unknown 的规则保留。

## 精确 XOR 集合

旧算法对两个有限集合做笛卡尔积；不同配对往往产生同一个结果。

第一条快路从实际集合的 AND、OR、严格有序唯一性和基数证明它是完整的独立位集合，再枚举精确 XOR 结果。它没有把两个未知值视为相同值。

第二条快路先按目标宽度零扩展/截断并去重，分别用集合首值平移，建立双方差向量的 GF(2) 联合基。只在维数至多六、共同空间至多 64 元时采用：

- 若两集合的基数之和严格大于空间大小，对任一空间元素 h，A 与 h XOR B 必相交，故结果恰好是整个平移后的空间。
- 其余情况将实际成员编码为 64 位 membership，逐项对第二集合做 XOR 索引置换并求并集，得到精确结果。不会把有缺洞的输入补成整个空间。

编码和解码使用同一组基。结果按实际数值重新排序；若已证明的结果超过 maxValues 则保持 Unknown。维数较大或不满足前提时使用原算法。投影、成员扫描、消元、位交换和输出枚举消耗预算；失败尝试的成本不退回，没有新增持久缓存或内存事实。

默认限制仍为 64 个值、4096 块、1000000 操作、262144 事实。预算失败继续使全部结果 Unknown，不发布执行前缀或部分目标。

## 真实语料

两个语料库的 69 个输入、138 个策略记录全部重新执行：旧库与新库各有 205018 个有效函数检查点，新库生成的 1671 个 V2 原始模块全部通过 verify。每个输入先完成旧库 Graph 对照，再完成新库 Graph 和全部有效函数的原始 IR 验证；没有使用历史 raw 结果，没有重跑旧库 LLVM 或本轮全量优化 IR。

276 份 canonical 流逐项合并核对，指令及解码字节、直接边、callee、块、函数成员和有效入口的增删改均为零。69 个输入、生产/验证源码及实际库字节在终态重新核对一致。两侧未提升记录均为 231798；既有的 6 个缺失 IGNIL 块、26 条通向未解码地址的边、3 个无效函数候选及 146 项线性 objdump 缺口逐项保留，未以排除或归一化消除。

最大实际生成并验证的单个 IR 为 362429756 字节。每项运行、审计、开发机流式封存和 VM 精确清理完成后才开始下一项；69 项均成功，无新增跳过或验证失败。独立前向审计重新核对保留的小记录、模块覆盖和封存链；它不重复解压大归档来重算原始 canonical 流。

测试库由 `a9f916d` 加冻结补丁构建。源码映射核对最终 Git 内容与开发机、VM 的 289 个代码文件和 37 个 SDK 文件一致；后续文档及 Git 发布不改变已验证的库字节，不冒称重新构建了发布后的 HEAD。记录保存在开发机及 VM 的 `call-analysis-cost-20261108/`。

真实语料的结构对照及 IR verify 不能证明整程序语义。任意堆初始化、跨调用未知写、一般循环归纳、未知目标和自动去平坦化仍不由这次成本优化解决。
