# LLVM Lift：跨函数控制流与调用边界（待实现）

状态：待做。派活方式见 `docs/agent-tasks.md`（任务 8）。开工前先读 `AGENTS.md`。

## 背景：现在的问题

基本块内的指令语义已经过多层对拍验证（单指令、真实块、LLVM 原生执行）。但**函数级的控制流和调用边界**在
LLVM 降级层（`lib/LLVMLifter.cpp`）存在两类确认的问题，而且以前的验证没有覆盖到：

1. **调用之后寄存器被当成没变**：CALL 降级成只带内存指针的调用，被调函数对寄存器的影响（返回值、
   调用者保存的寄存器）不可见。内部函数、外部导入函数、间接调用都一样。
2. **跳出函数范围的控制转移被降级成 `unreachable`**：目标不在本函数的 JMP、任一目标在函数外的条件跳转
   （条件尾调用）、未解析的间接跳转都是这样。LLVM 把 `unreachable` 视为未定义行为，优化器会删掉通向它的路径；
   条件跳转的情况下，连不跳转的那条正常路径也丢了。

以前没抓到的原因：`realblock_llvm.py` 只测直线代码块（call/jmp 在测试前被去掉），`corpus_check.py`
只检查 IR 是否合法（`opt -passes=verify`），不检查语义。

### 两个现成的失败用例（x86-64，函数起始 0x1000）

```
# 用例 A：调用结果被忽略
31c0          xor eax, eax
e8f90f0000    call 0x2000
85c0          test eax, eax
7407          je 0x1012
b901000000    mov ecx, 1
890b          mov dword ptr [rbx], ecx
c3            ret
# 现象：opt -O2 后，test/je 被折叠，写 [rbx] 的路径被删除（优化器认为调用后 eax 仍为 0）。

# 用例 B：条件尾调用
85ff          test edi, edi
0f84f81f0000  je 0x3000          ; 目标在函数外
c70307000000  mov dword ptr [rbx], 7
c3            ret
# 现象：未优化的 IR 中 CJMP 已经是 unreachable，不跳转路径没有前驱；opt -O2 后整个函数只剩 unreachable。
```

## 已经具备的基础（main 上可直接用）

- `LoadedImage::importSlots()`（b781218）：导入槽位地址 → 导入函数名。PE 是 IAT 表项；ELF 是
  JUMP_SLOT / GLOB_DAT 动态重定位指向的 GOT 槽位（x86-64 / i386 / AArch64 / ARM）。已对照 readelf 验证。
- x86 `ret imm16` 的额外出栈字节数记录在 IGNIL RET 的 `Op::aux`（cfca9b2），普通 `ret` 为 0。
- IGNIL 层的现状：x86/AArch64 的 IGNIL CALL 不压返回地址、RET 没有操作数（刻意的抽象，见 AGENTS.md）；
  SymbolicExecutor 把 CALL 当作块出口停止，不受第 1 类问题影响。BackwardSlicer 跨 CALL 时寄存器是否被当成不变，
  需要单独验证。

## 实施计划（按顺序，每步单独提交）

### 第 1 步：制定统一的状态和控制流契约
先写清楚、写进文档，再写代码：
- GuestState：寄存器文件的布局和所有权（谁读、谁写、何时同步）。
- PC、SP、Flags 的表示方式；内存状态的表示。
- 函数退出的原因（正常返回、跳出函数、未解析目标等）以及如何告知调用方。
- 跨函数分发接口：被调函数和未解析目标在 IR 中如何表示，使用者如何提供实现。
- 与现有 IGNIL 抽象（CALL/RET）的关系：在哪一层建模，哪些保持不变。

### 第 2 步：最小可用的跨函数分发出口
- 先解决跳出函数范围的 JMP 和条件跨界跳转（用例 B），不再生成 `unreachable`。
- 为未解析的目标保留一条运行时处理路径。
- 已解析跳转表的 switch，其 default 分支的处理方式也要按契约确定。

### 第 3 步：调用边界的状态同步
- 确保 LLVM 中缓存的寄存器值（alloca/SSA）与 Guest 寄存器文件之间不存在过期值。
- 调用产生的副作用必须能被正确观察（用例 A）。
- 默认保守：不假设被调函数遵守调用约定。是否提供按 ABI 假设的可选模式，在契约中说明。

### 第 4 步：完整的 Guest CALL/RET
- x86：CALL 压入返回地址；RET 读取返回地址，并用 `aux` 清理栈。x86-32 和 x86-64 都要覆盖。
- AArch64：BL/BLR 更新 X30；RET 使用指令指定的寄存器。

### 第 5 步：外部符号恢复与剩余的间接控制流
- 用 `importSlots()` 恢复可识别的外部函数名：PE 的 `call [__imp_X]`、ELF 的 PLT 桩和 `call [rip+GOT]`、
  导入跳板（thunk）。
- 完善间接 CALL/JMP 的分发。
- 注意：**给外部函数命名不等于实现了外部调用的语义**。命名之后，外部函数在 IR 里仍然是未知效果的调用。

### 第 6 步：执行对拍与整体回归
- 函数级执行对拍框架**从第 1 步就建立最小版本**，每一步先加入会失败的用例，再修复。
- 最终要做完整的函数级对拍：整个函数（含分支、循环、调用、尾调用、间接跳转）编译后原生运行，
  与 Unicorn 执行同一函数的结果比较（寄存器、标志位、XMM、写入的内存、栈指针）。被调用的外部目标在两边
  用相同行为的桩函数代替。
- 回归：全部 ctest、`corpus_check.py` 两套语料库、`realblock_llvm.py`、跳转表验证（wrong 必须保持 0）、
  toy-vm 测试（它用 LLVM JIT 执行 `liftBlock` 的结果，会受 CALL/RET 语义影响）。
