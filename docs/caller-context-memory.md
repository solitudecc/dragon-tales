# 从调用者事实实例化栈写效果

2026-11-08，基线 `5a57164`。在[有界调用树证明](stack-call-effects.md)上，
让可选的 `prove_leaf_calls` 分析使用调用点已经证明的寄存器常量和栈指针关系。
例如调用者先执行 `p = SP + offset; value = constant`，helper 执行
`*p = value; return`，现在可以推导这次调用的栈写范围和最终常量。
整个过程静态完成，不执行目标程序，也不依赖函数名、导入名或混淆器模板。

后续的[跨调用内存与循环阶段](call-memory-loops.md)扩展了内存事实传递和确定循环效果。
本文保留本阶段当时的能力边界与验证数字。

## 证明契约

先尝试原有的任意输入证明；成功时继续复用。失败时才构造调用点上下文，
独立证明同一 helper 在这些约束下的效果。上下文仅来自当前抽象状态中已证明的事实：

- 单个确定的寄存器字节常量；未约束字节仍是任意输入。
- 完整指针宽度、与当前 SP 同一符号空间的栈地址，换算成被调函数入口 SP 的偏移。
- 可选的完整数值入口 SP，只用于识别内存地址；普通整数计算不会因此被误标为栈地址。

约束是入口事实，不是机器寄存器写入。部分 EAX/ESP 约束不会凭空清零或确定 64 位父寄存器。
SP/RIP 不作为普通参数约束传入。上下文经过宽度、寄存器范围、重叠和预算校验；
没有传入被调函数入口内存，也没有导入初始化快照或全局/堆状态。

根分析和嵌套证明的缓存均使用“目标地址 + 完整规范化上下文”作键，
包含指针偏移、常量及可选数值 SP。不能复用上下文不匹配的结果；同一目标和相同上下文可以复用。
上下文只用于当前调用效果，不改变独立承认的 callee 入口，不给 Graph 增加假设。

每条已知 CFG 后继仍须参与汇合；不根据参数剪枝、不只取第一条返回路径。
循环扩大到不再是单个参数值时，不复用早先的单值证明。
所有正常返回必须恢复 SP，所有写入都重新检查本层和祖先返回槽。
CALL 压栈、helper STORE 和嵌套写范围先使调用者事实失效，之后才安装已证明的最终常量。

已知数值地址的 CALL 压栈或 STORE 若覆盖已解码指令字节，会拒绝调用证明。
检查包含重叠 x86 解码路径，较晚的短指令不会遮蔽较早长指令的尾部。
这只是固定代码模型的安全门禁，不是自修改代码支持；未知绝对地址仍受原有固定代码契约约束。

## 接口、预算和边界

没有新增公共 API、C/Python 结构、IGNIL 操作码或 Guest ABI。
继续显式开启原选项：

```python
facts = graph.finite_values(entry_points=entries, prove_leaf_calls=True)
with dragon.PassPipeline() as pipeline:
    pipeline.register_finite_dispatch(code, base, entry_points=entries)
    pipeline.add('finite-dispatch', prove_leaf_calls=1)
    report = pipeline.run(graph)
```

默认仍关闭。只读内存查询及条件入口查询也使用同一有限值集引擎；
本组件不会把条件查询的假设自动交给 Graph 目标恢复或 LLVM。

沿用无前缀 x86-32/x86-64 E8/C3、至多四层调用、每层 32 块、每层至多 8192 事实及
入口 SP 前后 1 MiB 写范围的限制。每次证明尝试的调用树共享最多 4096 次检查/操作；
任意输入尝试和上下文重试分别受此上限约束，两者都计入外层全局预算。
上下文描述、字节、构造操作和缓存占用也计入预算，缓存命中不会免除构造成本。
局部证明失败保持调用屏障；全局耗尽返回不完整/Unknown，不发布部分目标集。

一般参数指针别名、调用前内存事实传递、任意堆/全局写、外部调用、递归、一般符号返回表达式、
通用 `memset` 循环效果和基于参数的路径证明仍未实现。未知写入仍可能影响栈表。
本组件没有实现去平坦化、堆不透明谓词消除或生成去混淆后的新二进制。

## 验证

新增 14 个 C++ 回归覆盖两种 x86 位宽和两种解码策略，包括不同参数的重复调用、
嵌套调用、循环扩大、部分约束、独立 callee 入口、预算、返回槽及重叠代码写保护。
用匹配的 `5a57164` SDK/旧库运行同一测试文件，能够编译，14 个用例中 8 个失败、
6 个通过，563 条断言中 27 条失败。七个正例属于旧版能力不足；已知 CALL 压栈覆盖
代码的安全回归另有 12 条失败，不能把所有旧版 Unknown 都说成机器语义错误。
新主构建及无 Z3 构建均为 14/14、1094/1094 断言通过；
完整 CTest 分别为 729/729 和 597/597。

永久机器码夹具为 `tests/fixtures/caller-context.json`：i386/x64 各有单调用、双调用和
嵌套调用三种形状。独立参考脚本 `scripts/validation/caller_context_diff.py` 得到
48 次完整 Unicorn root 返回，比较全部 52/76 个建模字段和 64 KiB 内存；
结果、内存、DF 及清空单目标边集合的控制各检出 48/48 次故意差异。
新增只读 API 检查在两策略得到 12/12 精确 Finite，旧版相同查询均为 Unknown。
主构建和无 Z3 构建结果一致。Graph 查询前后及新旧默认指纹一致；
每种构建的九类坏报告控制均被拒绝。

完整函数执行复用未修改的 `finite_dispatch_diff.py`：主构建两策略 ×
V2/static/product × 原生 O0/O2 × 六夹具 × 八输入，576 次完整 root 返回匹配。
无 Z3 的 product 双策略另有 192 次完整匹配。比较全部建模字段、64 KiB 内存、
PC/SP 和退出记录，零 incomplete、差异、排除、跳过或归一化。
static/product 使用 FunctionStart 入口策略。所有计划使用同一六夹具和 48 个固定输入状态，
不能把重复参考执行当成新增独立样本。

冻结旧库开启相同 `prove_leaf_calls=True`，product 双策略的 192 次尝试均为
incomplete，完整返回为零；没有用跳过有限值集 pass 的 `--baseline` 作对照。

CFG 控制检出 12/12 次故意清空单目标集合，其执行语义仍完整匹配。
这些故意差异单列，不计入上面的 768 次正例。

没有执行 wrapper/megaInit 或注入堆快照。开启相同 `prove_leaf_calls=True` 后，
旧库、主构建及无 Z3 构建在 `0x1004f` 和 `0x1011b` 的各 192 个表单元查询都仍是 Unknown。
这些前缀不是完整函数执行，也没有新增真实 Tigress 完整恢复收益。
