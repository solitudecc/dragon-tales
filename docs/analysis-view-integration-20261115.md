## 最终目标与验收标准

用户于2026-11-15明确：**去混淆后的函数，应让分析者清楚看出混淆前的业务逻辑。**
后续组件以这一最终产物衡量收益，并逐项记录尚未解决的部分。

- **业务逻辑可辨认。** 输出能跟踪输入如何参与计算、产生返回值与输出内存；能看清
  真实条件、循环、索引和调用关系。可证明的 MBA、恒定谓词及混淆分发状态应被化简或
  消除；原程序的真实 switch、输入相关条件和循环保留。
- **输出适合阅读。** 业务视图恢复可证明的栈槽、变量与数据依赖，减少无关的寄存器
  快照和执行模型样板。源码逐字复原及原变量名不作为要求；完整状态 IR 保留用于验证。
  7150行执行模型反编译、行数减少或单独的 pass 计数均不能替代业务逻辑验收。
- **语义有依据。** 明确输入 ABI、可观察返回/内存、调用顺序、副作用和错误行为。
  入口条件与未知行为在产物中可见；无法证明的调用或内存效果保留，不为美化伪代码
  删除。完整状态验证与业务观察契约验证分别报告。
- **端到端对照。** 对自建样本交付混淆前业务源码、混淆后分析结果及优化后的 IR/伪代码，
  对照计算和控制结构并做独立执行验证。原源码只作为参考，不输入通用 pass 来生成答案。
  使用新种子及不同编译优化档复验，防止按函数名、地址或当前样本结构写死。

当前组合大样本仍有中央分发循环，业务视图和可读伪代码尚未交付，最终目标尚未达到。

## 首次拒绝已经定位

临时只读诊断用独立 `LLVMDispatchCorridor.cpp` DSO 覆盖已安装同 ABI 实现，原产品
源码、SDK 和输入不变；诊断不执行 Guest，不作为正式新产品验收。
保存私有 proof 模块与实际拒绝链，根为机器块 `bb_7741`（0x1e3d，对应原伪代码case78）：

```llvm
%652 = sub i32 3, %R11D.1
%653 = or i32 %652, %R11D.1
%654 = xor i32 %653, -1
%655 = lshr i32 %654, 27
%656 = and i32 %655, 16
%narrow555 = add nuw nsw i32 %656, 60
%657 = zext nneg i32 %narrow555 to i64
```

旧证明器只把 i1 / AND1 看成不需要数值求解的二值观察，因此继续追入历史
`R11D.1` PHI 后拒绝。此处不需要知道该循环变量的具体值：`%656` 的完整域是
`{0,16}`，选择器域是 `{60,76}`；这是保留真实业务条件的有限域，不是证明条件恒定。
首个失败来自此业务循环条件，不能预先归因为某个全局不透明谓词。

当前候选实现仅扩展 batch 的二值观察：任意位置的 one-hot AND、无 exact 等标志的
最高位逻辑右移。原始选择器仍在同一位置执行/消费，不导出 definedness；上层算术
flags 仍对两个赋值全部检查。多位 mask、独立第二观察、字面 undef/poison 和未证明的
flags 继续拒绝；legacy 单边 API 的域保持不变。不加入样本地址/名称规则。

临时候选已越过原首个拒绝，默认原1,000,000总work内随后遇到

**这仍是 Incomplete，不代表批次或完整循环证明已经通过。** 后续应定位重复证明成本，
