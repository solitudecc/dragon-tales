# 只登记已解码的自动入口

2026-11-09，基线 `83e8c8c`。本阶段修正 x86 和 ARM 自动分析的入口登记，
以及依赖这些登记的跨节恢复，不改指令解码、提升语义、有限值分析、LLVM 优化器、
公共 API 或 Guest ABI。

## 候选目标与可用入口

真实的 CALL/JMP 可以指向当前输入之外、截断指令或不可解码的地址。旧实现会先将
这些地址加入 Graph 的有效块和函数集合，即使 `graph.get(address)` 为空。
这使集合宣称入口存在，而 BasicBlock/Function 视图没有第一条机器指令，随后出现
缺失 IGNIL 或无效函数候选告警。

自动登记现在要求第一条指令已解码。真实的 `branches`、`callees` 和条件跳转的
隐式顺序后继仍然保留，包括指向地址零的边；没有把未知目标当成不可达，也没有
使用“地址必须非零”的判断。地址零确有代码时，照常登记并提升。

这是自动分析器的规则。公共 `Graph::addBlock/addFunction` 仍允许调用者先登记
地址，供手工构图和纯 IGNIL 使用；不能据此断言所有 Graph 的有效地址集合都具有
机器指令。LLVM 的无块函数拒绝测试改为显式创建同一个无效视图，原有拒绝、模块
无部分输出及相邻正常函数检查全部保留。

## 分段分析和跨节恢复

目标可能在后续输入片段中才出现，或已由另一节的顺序路径解码，且处于该路径内部。
每次提交在解码扩展之后重新检查已有指令的真实控制流证据：已解码的分支目标登记为
块，已解码的被调函数同时登记为块和函数，已解码的条件顺序后继登记为块。
随后沿现有分割和提升逻辑更新对应视图及 IGNIL。

检查既用于首次直接恢复，也用于每一轮间接候选扩展后的提交。在初始扫描之后、
直接恢复之前仅检查一次仍然不够：当真实 CALL 的目标是刚刚补解出的重叠入口，
或在后续间接扩展中才出现，会漏掉其函数分类。候选图只更新自己的地址集合；
失败假设撤回时，相应入口、块分割及 IGNIL 一并撤回，不提前污染正式 Graph。

这里仅重新登记已经解码的目标。尚未解码的条件顺序后继仍由加载器的入口恢复处理，
保留原来的独立根策略。若把所有历史目标提前放入 x86 重叠解码队列，会改变这一
策略；永久跨节用例检出了该中间版本的问题，最终版本没有放宽测试。

加载器不能再用空登记作为跨节恢复的唯一线索，因此同时读取指令上的分支、被调
函数及条件跳转顺序后继。仅接受目标节内有文件字节、尚未解码的地址，不将普通
指令或 CALL 的顺序地址扩成额外入口。每轮逐节重新收集，以便本轮早先发现的边能
交给后面的节；原有八轮上限保持不变，不承诺任意长的跨节依赖都能完成。

修复历史证据重放后原检查通过。失败版本的完整原生输出不宣称已全部归档；
保留的是当时的 CTest 输出及后续专门的回归和运行证据。

## 独立 CPU 与原生执行

四个永久机器码夹具覆盖 i386/x64 的 CALL 0 和 JMP 0。完整 root 路径通过已知
标志位绕过这条外部边，实际向客体内存写表后间接跳转并返回；另从外部传输点
单独执行，验证 CALL 的真实压栈及 JMP 行为，不继续执行地址零。

独立顺序模型与 64 次完整 Unicorn 返回、64 次明确边界执行一致，共比较
8192 个建模字段及 8388608 内存字节。结果、单字节内存、AF、目标控制分别
检出 128 次单项错误；没有排除、跳过、归一化、调用桩或 CPU 观察目标提示。
边界检查与完整返回分开统计，不将边界退出算成函数执行成功。

最终 v4 主库的 V2/static/product、两种策略、O0/O2、16 个输入合计 768 次完整
原生返回，无 Z3 product 另有 256 次，正常新版共 1024 次。比较 65536 个
建模字段、全部七个 Exit 字段及 67108864 内存字节，差异和提前退出为零。
结果、内存、缺边控制各 64 次，单列于正常输入；缺边控制删除唯一目标登记，
原生执行仍匹配，但 64 项缺失登记全部被检出。

旧主库对应的冻结 256 次完整返回也匹配，因此这里证明兼容性与测试判错能力，
不宣称新增这些夹具的返回覆盖。最终版新执行共 1216 次，旧 256 次和独立 CPU
128 次使用已冻结证据，分别记账。中间 v3 的矩阵及其独立复核另行保留，不计入
最终版新执行数。最终版独立复核实际检查了 88 个编译程序、176 项 IR 证书绑定，
重新计算 77824 个建模字段及 79691776 内存字节，并检查全部七个 Exit 字段。
1216 个原生进程轨迹中，256 个 V2 进程加载最终主库，960 个独立程序没有
Dragon 依赖，11 个 Python 前端的实际库记录均匹配最终 pins。复核不重新
执行 CPU、Graph、LLVM 或 opt，也不将重复输入或审计次数增加为新样本。

## 真实输入定位

`corpus2-cxx_mingw32_O2.exe` 两种策略原先各有地址零的一个缺失 IGNIL 块和
一个无效函数候选。实际 E9 机器码确实给出 13 条指向零的边，LLVM objdump
也确认这些位移。新版不再登记空入口，但每种策略的 13 条真实未解码边仍保留；
线性策略逐项比较源地址、目标和字节均不变。

`corpus2-sys_libcrypto.so` 线性策略的四个空块地址是 `0x2ceb2c`、`0x4c06c0`、
`0x997370` 和 `0x7aa75f4`，其中前者还登记成函数。这些地址没有已解码首指令，
有的属于数据或输入范围之外。新版专门定位结果的缺失块和无效函数均为零。
该定位脚本只为 C++ 输入枚举未解码边，不能用它的 crypto 空边列表证明边覆盖；
全语料检查另有完整边审计。单次计时受资源状态影响，不作性能收益结论。
